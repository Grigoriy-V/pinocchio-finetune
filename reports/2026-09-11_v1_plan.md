# v1: the plan, the numbers, the open risks

Written 2026-09-11 when the repository was created (harness roadmap 24,
step 4). Everything below is what was read and computed; nothing has run
on a GPU yet.

## The set

From the harness export of 2026-09-11 (447 runs), `tune/convert.py` with
the report's filter keeps 260 runs — 251 passed by the checks and the 9
V7 runs whose only failed check was dropped after the run — and 814
model calls. Teacher token count from the calls' own usage: 4.37M
prompt+completion tokens per epoch, mean 5.4k per sample, the longest
about 8k — of which only 33k are completion tokens. The loss sees 41
tokens per sample on average: the signal is the tool call and the short
final answer, the prompt is context. That is the shape of agent data, and
why a few hundred trajectories can still move a model; it is also why
training loss will be noisy step to step. No call carried media. By family: D 22, L 42, N 44, T 54,
U 45, V 36+9, X 17 runs.

## Choices

| choice | what | why |
|---|---|---|
| base | `google/gemma-4-12B-it` bf16, NF4 at train time | the harness serves a QAT int4 compressed-tensors checkpoint; LoRA over it in vLLM has a rank-32 correctness bug (vllm #50059) and NF4 is a different quantization anyway |
| loss | completion only, one sample per model call | every call of a trajectory becomes a sample whose prompt is exactly what the model saw; earlier assistant turns are context, not targets |
| masking | pre-tokenized `input_ids` + `completion_mask` | Gemma's template has no `{% generation %}` markers; rendering prompt and prompt+completion and checking the prefix is exact and fails on CPU |
| tool calls | `arguments` as JSON strings in the JSONL, a mapping at render time | Gemma's template refuses a string (found by the first `tokenize`, 814/814 rejected, cents); the string keeps Arrow schemas flat |
| LoRA | r=16, α=32, all linears of the language model, dropout 0.05 | the research report's settled values; the multimodal towers frozen and kept so the merge still serves images |
| schedule | lr 2e-4 cosine, warmup 5 %, 2 epochs, batch 1 × ga 8 | 814 samples → ~102 steps/epoch, 204 steps |
| ceiling | 12,288 tokens, over-long samples dropped, never cut | a cut trajectory teaches a cut answer |
| GPU | L40S 48 GB | 12B NF4 ≈ 8 GB + activations at 8k with checkpointing; A100-40 is the fallback if it does not fit |
| serving | merged bf16 on L40S, vLLM 0.26.0 / transformers 5.14.1, the harness's Gemma flags | one artefact per run, the pair the harness validated |

## Open risks, to be answered by the smoke run

1. **Versions.** `transformers==5.14.1` is the pair the harness validated
   for Gemma 4 in vLLM; TRL, PEFT and bitsandbytes are pinned by floor
   only. The first `tokenize` and the smoke run say whether they agree.
2. **The model class.** `AutoModelForImageTextToText` for a multimodal
   Gemma 4 with a 4-bit language stack and a LoRA regex on
   `language_model` — if the regex matches nothing or bitsandbytes
   refuses the towers, the smoke run fails at load, at cents.
3. **The template on our shapes.** Later system messages (the harness's
   "facts" context) and tool messages by `tool_call_id`: `tokenize`
   reports every sample the template rejects, before any GPU.
4. **The hand-back.** The harness's `MODEL_TUNED_API_KEY` proxy token and
   the `[model.sets.tuned]` entry are a harness change and a gate there.

## What the first `tokenize` runs found (2026-09-11, two CPU runs, cents)

1. Gemma's official template (published 2026-07-09, "fixed tool-calling
   loops, turn closures, and thinking content-ordering") refuses tool-call
   arguments as strings: 814/814 rejected. Arguments are made mappings at
   render time; the JSONL keeps strings.
2. With the prefix check, 513 of 814 held; 301 did not — reproduced
   locally, string for string, with the template read from the Volume's
   cache and jinja2, so the rest was worked out without a worker:
   - **269, every first call of a run:** with thinking off, the generation
     prompt ends in an empty thought channel `<|channel>thought\n<channel|>`
     that a stored assistant turn is never rendered with. That is what
     vLLM builds at inference, so the sample is now the prompt as rendered
     with the generation prompt plus the target cut from the full render
     after `<|turn>model\n`.
   - **32, a prior assistant turn that carried text together with a tool
     call:** the template renders such a turn as call → tool response →
     text and then closes the model turn with `<turn|>`; the next assistant
     message is glued into that closed turn. The prompt the model sees at
     inference ends in a closed turn with no generation prompt at all, so
     there is no target consistent with inference. Dropped, 782 remain.
     This is an inference-time property of the template as the harness
     uses it through vLLM, not of the data: whenever a model writes text
     with a call, the next request to Gemma starts from a closed turn. It
     is an observation for the harness's owner, recorded here, not acted
     on.
   - A trailing tool call is rendered with an opened, empty
     `<|tool_response>` after it; the target cuts it, since the model stops
     at `<tool_call|>` (one of the three stop tokens). A text target keeps
     its `<turn|>`.
   - A completion that carried text with its call (32 of the 814) trains
     as the call alone, because in Gemma's DSL that text belongs after the
     response.
   Locally: 782 targets, 531 of them tool calls of the shape
   `<|tool_call>call:…<tool_call|>`, 251 text ending in `<turn|>`.
